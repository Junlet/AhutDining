## 需求 1 的一个前提（重要）

工作区里的 **PocketAHUT 仓库只有文档、没有菜品数据**（数据在它闭源 App 的后端里）。
所以本项目：

* **食堂/窗口结构**参考了 `PocketAHUT/docs/features/canteen.md` 的描述（本部 + 东区、按窗口划分、比价、窗口评分）；
* **菜品数值是示例数据**（61 道安工大常见菜式，营养素按 4/9/4 估算，见 `data/dishes_sample.csv`）；
* 一旦拿到真实菜单，用 `tools/import_dishes.py --file 你的文件.csv --replace` 一条命令替换，
  推荐算法、分数、记录全部自动跟着变，不需要改代码。

## 导航与推荐模式（2026-11 调整）

导航从 7 个标签简化为 6 个：**推荐 / 今日 / 搜索 / 自选评估 / 收藏 / 设置**。

* 「今日计划」与「用餐记录」合并为「今日」：一页同时看今日计划（每餐卡片）与当天记录合计，
  支持日期回看历史记录；补记/修改/清空都在同一个页面完成。
* 「推荐」页的行为由设置里的 **推荐模式** 决定：
  * `single` 单道菜：只推荐当前这一餐的套餐（一次 6 套可刷新）；
  * `day` 一天方案（默认）：按当前时间 + 用餐记录算出还剩几餐，给 A/B/C 三套整日方案；
    选定后成为今日计划，页面自动跳到「今日」。
* 模式存在 `settings.recommend.mode`，通过 `PUT /api/settings` 修改，前端即时生效。
## 追加需求：今日用餐计划（整天一起推荐）

### 判定"今天还剩几餐"

对用户设置里的每一餐（按 `meals_per_day` 展开的早/午/晚/加餐），依次判断：

| 状态 | 条件 | 表现 |
|------|------|------|
| 已记录 `recorded` | 该餐在 `meal_records` 里是 `confirmed` 或 `manual` | 显示实际摄入，不再推荐 |
| 已错过 `missed` | 该餐时间窗已过且没有记录 | 默认不推荐（例如早餐没过记录、已到中午 → 只剩午餐+晚餐）；勾选「包含已过时段」可补排 |
| 待安排 `planned` | 未记录且时间还没过（或正在进行中） | 生成推荐 |

时间窗取自设置里的 `slot.breakfast/lunch/dinner.start/end`，判断基准是本机当前时间。

### 怎么分配额度

1. 取今日总量：`每日目标 - 已确认摄入` = 今日剩余额度（蛋白/脂肪/碳水同理）；
2. 剩余餐次按各自 share（早餐 0.3 / 午餐 0.4 / 晚餐 0.3）分这份额度；
3. **已被固定的餐**先占额度，后面的餐按剩下的额度重新分配——所以"固定午餐"后刷新，晚餐会自动围绕午餐调整；
4. 每餐在该餐次候选组合里按 `score^4` 加权抽一个（同分不同批，刷新会换内容）。

### 每天第一次打开：先给 A/B/C 三套整日方案

```
进入「今日计划」
   ├─ 当天还没有方案 → 按当前时间算出"还剩几餐"，给出 方案A / 方案B / 方案C
   │     ├─ 选一套 → 其它两套收起，成为「今日用餐计划」
   │     └─ 都不满意 → 「换一批方案」再抽一批 A/B/C
   └─ 当天已选过 → 直接回放已选的今日计划
```

三套方案不是同一份换个顺序：每套用不同的随机种子生成，且要求"菜品组合不同"，
每套都自带整日热量、蛋白/脂肪/碳水、花费、平均推荐度（A/B/C 的分数会有差异，供比较）。

| 刷新整日（保留固定餐） | 「刷新未固定的餐」 | `POST /api/day-plan/refresh` | 固定餐原样保留，其余重新抽，额度围绕固定餐重排 |
| 单餐刷新 | 每餐卡的「刷新这一餐」 | `POST /api/day-plan/refresh {only_meal}` | 其余餐全锁定，只换这一餐 |
| 固定 / 取消固定 | 每餐卡的「固定这餐」 | `POST /api/day-plan/pin` | 只改标记，不动内容 |

### "推荐度"是怎么算的

* **单餐推荐度**：这一餐的菜品加总后，按 `评分 = 0.30×热量匹配 + 0.30×蛋白占比 + 0.20×脂肪占比 + 0.20×碳水占比`（区间内满分、越界线性衰减），
  再叠加多样性/口味/价格与单菜营养分，得到 0–1 的分值；映射为 **强烈推荐(≥0.85) / 推荐(≥0.70) / 一般(≥0.55) / 不推荐**。
* **整日推荐度**：各餐推荐度的平均值（只统计有内容的餐次），方案卡与计划头部展示。
* 用户自选一道菜替换时，推荐度会**立即下降并给出原因**（例如"碳水占比偏高""蛋白质不足"），
  这正是"自动补齐"要解决的问题：补 1–3 道后分数通常会回到「推荐」。

### 边界情况

* **过了早餐时间又没记早餐**：早餐标为「已错过」且不推荐，整日方案只排午餐 + 晚餐（这是需求里的默认行为）；
* **深夜所有时段都过了、又没有任何记录**：自动把全天重新排上（`auto_include_passed`），
  返回 `suggest_include_passed` 让前端提示；也可以手动勾选/取消「包含已过时段」；
* **只吃 1–2 餐**：目标大，单餐需要 6 样左右才够，因此大目标时允许再补一份主食（仍不会出现三碗米饭）；
* **加餐（4 餐及以上）**：`snack` 按全天 12% 目标，候选来自水果/饮品/小吃；
* **已确认的餐**：状态优先记为 `recorded`，不会因为固定标记而被改回推荐。


## 单餐推荐链路（对应需求 2/3/4/5/6/7）

```
用户资料 ──► BMR(Mifflin-St Jeor) × 活动系数 = TDEE
              × 目标系数（保持/减脂 0.85/增肌 1.10） = 每日目标热量
              ──► macro_targets() 按 AMDR 拆成 蛋白/脂肪/碳水 克数
              ──► ÷ 餐次比例 = 单餐目标
今天已确认的餐 ──► 剩余额度 ──► 按"剩余餐次占比"缩放本餐目标（夹在 0.5~1.35 倍）
              ──► 枚举各食堂「主食+荤+素(+汤)」组合
              ──► 逐套打分：热量匹配 30% + 蛋白 30% + 脂肪 20% + 碳水 20%
                             再加 多样性/口味(收藏与评分)/价格/单菜营养分
              ──► 跨食堂轮转取前 N 套 = 本次推荐
```

## 已知限制与待确认

1. **菜品数据是示例**：真实菜单需要你导入（见上）。营养素是全量估算值，误差主要来自"一份"的实际克数。
2. **膳食指南版本**：官方最新为 2022 版；你说的"2025"若指其它文件，把数值给我即可替换 `app/nutrition.py::AMDR`。
3. **固定时间点刷新**：桌面程序没有后台常驻进程，采取"前端每 30 秒查询当前时段 + 跨时段自动重新生成推荐"的方式，
   效果等同于定时刷新；若希望真正定时（例如 11:00 自动预生成），可再加一个 `--worker` 模式。
4. **图片存储**：存在本机 `media/` 目录（已 gitignore），换机器需自行拷贝。
5. **多用户**：按确认的方案做单机单用户免登录，但表结构保留了 `user_id` 字段，后续加登录成本很低。
